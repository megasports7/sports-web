# M7 — Web Application Build: Architecture Contract

## Context

M5 (Firebase → Supabase mobile cutover) is complete and independently verified through Phase 11 (see `sports-mobile-main/docs/M5_CONTRACT.md`). M6 (production cutover) is deliberately paused. This contract covers M7 — building `sports-web`, a Next.js web app on the same Supabase backend the mobile app already uses.

Decided in `docs/MILESTONES.md` before this contract: Next.js on Vercel, `@supabase/ssr` cookie sessions. Everything else here was worked out across this design conversation and is settled, not open.

## Scope (v1)

- Roles served: **player and organizer only**. Referee, associate, and admin are out of scope for v1 — added later by extending the same pattern, not redesigning it.
- Surface: **entirely behind login**. No anonymous/public pages in v1 (this supersedes `MILESTONES.md`'s original "event discovery/public cert lookup" framing for v1 — that framing assumed a public surface; the actual product decision made in this conversation is an authenticated dashboard, matching what the mobile app already is).
- Backend: the **same Supabase project** mobile already uses. No new project, no schema changes required by this contract — the whole existing RLS/RPC surface from M5 is reused as-is.

## Non-goals (explicitly out of scope for v1)

- No Server Components or Server Actions for data fetching/mutation.
- No custom backend or Next.js API routes layer. If a genuine server-side secret is ever needed (a third-party SMS/email provider, a future payment gateway for event fees), that's a Supabase Edge Function — the same mechanism mobile already uses for `migrate-password` — never a bespoke Next.js API route.
- No `service_role` key anywhere in this codebase, ever.
- No password-reset, credential-change, or forced-reset mechanism of any kind — per the standing "real user credentials are never touched by any mechanism" rule already governing M5/M6. If self-service password reset is ever wanted, it goes through Supabase's own built-in email-reset flow, unchanged — never custom logic, and only after an explicit ask.
- No SWR/React Query or other data-fetching library at launch — plain `useState`/`useEffect` per screen, matching mobile's existing manual-refetch pattern. Named exception, not a closed door: organizer's batch/bracket/dashboard screens can show the same underlying rows in multiple places, and mobile's own manual-refetch-after-mutation pattern is a known place for a "forgot to refresh the other screen" bug to hide. If that bug actually shows up during implementation, add React Query then, targeted to the screens that need it — it layers on top of the existing Supabase calls without requiring anything already built to be rewritten. Don't add it preemptively.

These are deliberate YAGNI cuts for a <1,000-user authenticated app on a tight timeline, not omissions to revisit reflexively — only reopen one if a real, observed need forces it.

## Execution-agent architecture (hard constraint — max 3 agents, fixed roles)

Same discipline `M5_CONTRACT.md` ran on the mobile migration, carried over unchanged: **brain** (Sonnet — decisions, contract/report writing, gate judging), **coding** (Sonnet — implementation), **reading** (Haiku — read-only verification, independently re-derives claims rather than trusting a self-report). No 4th role, no unbounded parallelism, at most 3 agents active at any point across the whole phased sequence below. The same reason it mattered for M5 applies here: the thing writing a check should not also be the thing that gets to grade it.

## Architecture

**One backend, one middleware file, plain client-side calls everywhere else.**

- **Framework:** Next.js App Router, deployed on Vercel.
- **Session handling — the one place real complexity is allowed to live:** `middleware.ts`, following Supabase's current documented `@supabase/ssr` pattern near-verbatim. It calls `supabase.auth.getClaims()` on every request, refreshes the session cookie, and redirects to `/login` when there is no valid session. Because the whole app is behind login (per Scope above), the middleware matcher protects everything except `/login`, `/signup`, static assets, and Next internals — no public-route allowlist to maintain.
- **Role-aware routing:** mobile's Auth Hook already injects `role` into the JWT as `app_metadata.role` (this is what `jwt_role()` in `supabase/migrations/20260826090000_rls_helpers.sql` reads, and what every RLS policy is written against). `middleware.ts` reads `claims.app_metadata.role` from the same `getClaims()` call to route a player away from `/organizer/*` (and vice versa) — no extra profile fetch needed for this coarse routing decision.
- **This role check is UX, not the security boundary.** RLS is what actually stops a player from reading or writing organizer-owned rows, independently proven from a generic HTTP client in M5 Phase 9. Even if a request bypassed the middleware redirect entirely, Postgres still enforces the real rule. This must never be treated as a substitute for an RLS policy.
- **Everything else is a Client Component calling `createBrowserClient()` directly** (the `@supabase/ssr` browser client) — events, registration, profile, organizer's event/batch/attendance management, login, and signup. No Server Components or Server Actions in the data path at all for v1.

## API layer: direct close port, not a rewrite

`player.api.ts` and `organizer.api.ts` (from `sports-mobile-main/src/api/`) are ported into `sports-web` nearly as-is:

- Same function names, same RPC calls (`register_for_event`, `create_batch_with_bracket`, `find_player_by_qr`, etc.), same `{success, data, message}` envelope, same business logic (e.g. `player.api.ts`'s generic "Invalid credentials" on role mismatch, which deliberately doesn't reveal whether the email exists under a different role — carried over unchanged).
- Adapted only where the browser genuinely differs from React Native:
  - `createBrowserClient()` (from `@supabase/ssr`) in place of the mobile `createClient()`/SecureStore adapter — the browser's own cookie-backed session storage replaces SecureStore; no hand-rolled storage adapter needed.
  - Real `File`/`Blob` for Storage uploads (`profile-photos`) in place of mobile's `expo-file-system` base64 workaround — genuinely simpler on web, not a new problem to solve.
- This is translation, not redesign. It maximizes behavioral parity with mobile (same edge cases, same error shapes) and keeps the door open to extend to referee/associate/admin later by repeating the same port, not inventing a new pattern.

## Route structure

Two plain route trees, `app/player/...` and `app/organizer/...` (**not** Next.js's `(group)` parenthetical syntax — that hides the segment from the URL, which would break `proxy.ts`'s pathname-prefix role check; corrected here after Phase 1 implementation, the design intent was always the literal `/player`, `/organizer` URLs already used throughout this contract's screen inventory). Each has a lightweight client-side auth context mirroring mobile's `AuthContext.tsx` (`onAuthStateChange` + a `profiles` fetch for display data) driving navigation — backed underneath by `proxy.ts`'s coarse gate and RLS's real gate.

## Environment / secrets

- Reuses the mobile app's existing Supabase project — same `SUPABASE_URL`, same public anon/publishable key (whichever key format the project currently issues; it's a public-by-design key either way).
- Exposed as `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` (Next.js's client-exposure convention, equivalent to mobile's `EXPO_PUBLIC_` prefix).
- `SUPABASE_SERVICE_ROLE_KEY` must never be added to this project — no server-side privileged bypass exists in this architecture, so there is no legitimate reason for it to appear.

## Safety and scale (recorded for reference, not a new decision)

- **Security:** unchanged from mobile — RLS enforces identical row-level rules regardless of client platform. The only new code is `middleware.ts`'s session-refresh, copied from Supabase's own documented pattern. Worth doing once, cheaply: re-run an M5-Phase-7-style secret scan against the deployed web build before considering v1 done, to confirm no privileged key ever made it into a client bundle.
- **Scale:** the browser client is stateless HTTP to PostgREST/GoTrue (no persistent DB connection per browser tab); Supabase's connection pooling absorbs concurrency behind that. For under 1,000 registered users, even worst-case peak concurrency (everyone registering for one event at once) sits comfortably inside what even a small Supabase compute tier handles with zero caching or CDN work. This architecture would need roughly a 10-100x growth in sustained concurrent load before it stopped being "seamless" — and at that point the fix is a compute tier upgrade, not a rewrite.

## Definition of done for the auth gate

Following the same "a check must be proven able to fail before its PASS means anything" discipline M5 ran on every new check:

1. Hit a protected route with no session → confirm redirect to `/login`.
2. Hit `/organizer/*` with a player-role session → confirm redirect.
3. Hit `/organizer/*` with a legitimate organizer-role session → confirm access.

Only after all three are observed (not assumed) is `middleware.ts` trusted.

### Phase 3.5 — QR-scanning follow-up (the 3 screens deferred in Phase 3) — ✅ complete, 2026-09-05
**Scope decision, resolved via user discussion:** camera-based scanning, uniformly across phone and laptop browsers — no USB-scanner-as-keyboard-wedge alternative (considered, explicitly rejected). `getUserMedia` treats a laptop's built-in webcam the same as a phone's camera; the only device-aware detail is `facingMode: {ideal: 'environment'}`, a preference that correctly picks a phone's rear camera and degrades gracefully to whatever a laptop has. Decoding via `jsQR` (small, dependency-free) rather than the native `BarcodeDetector` API, which has no Safari/iOS support at all.

**A pre-existing, previously-invisible defect found before writing any scanning code, not after:** going through the actual RPC definitions (per the user's explicit ask to implement carefully against the app's existing rules) found that `find_player_by_qr` and `scan_for_list` resolve a scanned code *only* via `profiles.legacy_id` — present only for the ~91 migrated accounts. Every self-signup player (every real new player going forward, on mobile or web) has `legacy_id = NULL`, so their ID card's QR renders as the literal broken string `"PLAYER:null"` and can never be resolved by either function. This predates M7 entirely and was invisible until scanning was about to be built. **User decision: fix it**, not port it faithfully-but-broken.

**Fix, via the Supabase migration gate (contract before SQL, live catalog not files):**
- Verified live before writing anything: `supabase migration list` showed zero drift between local files and remote history; direct `pg_get_functiondef` queries (Docker wasn't available for the CLI's own `db dump`, so connected directly via `pg` instead) confirmed the live function bodies — with one honest note, not swept aside: the live versions carry a couple of explanatory comments absent from the migration file text, meaning some out-of-band change happened outside the tracked migration history at some point. Functionally identical predicates either way.
- `sports-mobile-main/supabase/migrations/20260905130000_qr_resolve_by_uuid.sql`: both RPCs gain an additive uuid-matching branch, tried only when the existing digit parse finds nothing. Every existing legacy QR code keeps resolving exactly as before.
- **The migration's own mandated positive-control test caught a real bug in it within minutes**, before anything downstream relied on it: the digit regex, being unanchored, was tried *first* and greedily matched the leading digit run of a uuid (`0387` out of `0387fb8e-...`), stealing the branch before the uuid pattern ever ran. Fixed by `20260905131500_fix_qr_uuid_regex_ordering.sql` — uuid pattern tried first (far more specific; a real uuid can never accidentally satisfy the digit-only patterns, unlike the reverse, which just proved unsafe). Recorded as a superseding migration rather than a silent edit, matching this project's own established convention (`find_player_by_qr`'s original single-argument version was dropped, not rewritten, back in `20260826150100`).
- Both migrations `db push --dry-run`'d then pushed for real; live `pg_get_functiondef` re-queried after each to confirm, not assumed from the CLI's own success message.
- **11/11 positive/negative/legacy-untouched checks passed** after the fix, using one throwaway organizer + one legacy_id-NULL throwaway player: uuid-form QR resolves correctly; garbage still correctly rejected as invalid; a well-formed-but-non-matching legacy digit string still correctly returns not-found rather than erroring (proves the legacy path is genuinely untouched); `scan_for_list`'s uuid-keyed dedup still works. Cleanup confirmed by status code.
- **Out of scope, flagged not fixed:** `sports-mobile-main`'s own `PlayerIDCard.tsx` has the identical defect and would need the equivalent client-side fix to benefit from this migration — a different app's code, named here rather than touched.

**A second real bug found and fixed while adapting `scanAttendance`, not a byte-port:** mobile's version matches a resolved player to a registration by comparing `legacy_id` values — since `legacy_id` is `NULL` for every self-signup player and `null === null` is `true` in JavaScript, this would silently mark *any* self-signup player's registration when scanning *any other* self-signup player's badge, misattributing attendance between two different students. The exact failure this whole phase was started to prevent. **Fixed**: looks up the registration directly by the resolved player's real uuid instead (always present, never collides). This is a pre-existing latent bug in the mobile app too — flagged, not silently fixed there, since that's a different codebase.

**Built:**
- `src/lib/qr/QrScanner.tsx` — the one shared camera component used identically by all three pages and both device types; permission-state handling (requesting/denied/no-camera/error), an internal repeat-suppression so a still-visible code doesn't re-fire every frame, full cleanup (stops all tracks) on unmount.
- `organizer.api.ts` gains back `getPlayerByQR`, `scanAttendance` (adapted per above), `scanForList`, `getAttendanceListScans`.
- Three pages: `/organizer/events/:id/scan-attendance` (mobile's no-auto-timeout gate — resumed only by the user's own action), `/organizer/lists/:id/scan` (mobile's 1.5s auto-resume debounce + 50-entry capped recent-scans list + 3-way success/duplicate/error classification, faithfully ported), `/organizer/events/:id/rapid-mode` (full TANDING/SENI category cascade reusing `registrationCategories.ts`, real uuid-based dedup replacing mobile's dead JSON-parse-based check, and **`eventId` now actually passed to `getPlayerByQR`** — mobile's own call site deliberately never did, per `organizer.api.ts`'s comment calling that "still non-functional the same way it was before this phase"; fixed here since this is a fresh build with `eventId` already on hand from the route, not a literal port of a known-broken call site).
- Navigation wired: the events list links to both new scan pages per event; `CreateList`'s past-lists rows now link to the real scan page (previously nowhere to go, since the destination didn't exist yet in Phase 3).
- Build and lint both clean — one real `react-hooks/refs` finding fixed (a "keep latest callback" ref assigned during render, moved into an effect).

**Verified, not assumed:** a dedicated proof reproducing the exact scenario the `scanAttendance` fix targets — two throwaway self-signup players (both confirmed `legacy_id` NULL) registered for the same event — confirmed scanning player 1's QR marks *only* player 1 present, never player 2, and both independently mark correctly when scanned in turn. **9/9 checks passed**, cleanup confirmed.

**Honest boundary, stated plainly:** none of this exercises the actual camera/`jsQR` decode loop from this environment — there is no browser here to hold a phone up to. What's verified is every RPC and client-side data-flow decision downstream of "a decoded string arrived" (which is the part with real correctness risk, and where both bugs above were actually found) — the camera capture itself needs a real device to confirm, same class of gap already named for every prior phase's page-level verification.

### Phase 5 — Admin role port — ✅ backend built, 2026-09-05 (deliberately NOT exercised — see below; frontend design pass deferred, same as Phase 2/3/4)
**Scope, per explicit instruction:** build the same way as player/organizer/referee -- plan first (presented and implicitly approved before any code was written), backend + the UI it reflects in, **but administrative actions are not to be tested at all**, not even against throwaway accounts. **A real, previously-invisible bug found while reading the source before writing any code — the third occurrence of a pattern this project has now found twice before (the QR ID-card encoding and `scanAttendance`'s player-matching, both Phase 3.5):** mobile's `AdminUserList.tsx` builds every row's id as `p.player_id || p.id` (legacy_id with a uuid fallback — same for organizer/referee), then `updateUser`/`deleteUser` look that row up via `.eq('legacy_id', userId)`. For any self-signup account — `legacy_id` is `NULL` — the `||` falls through to the real **uuid string**, which then gets compared against a numeric column. **Editing or suspending any non-legacy player/organizer/referee through mobile's admin panel silently fails today.** Fixed in the web port: `updateUser`/`deleteUser` key directly on `profiles.id` (the real uuid, always present, globally unique — no per-role disambiguation needed) instead of `legacy_id`, which also matches what `admin-update-user`'s own validation already requires natively (it rejects anything that isn't a uuid) — this removes a lookup step rather than adding one. **Not fixed in mobile itself** — a different codebase, flagged rather than silently patched, same treatment as `PlayerIDCard.tsx`'s equivalent QR defect in Phase 3.5.

**Honest scope-of-proof statement, stated plainly, different in kind from every prior phase:** unlike Phase 0-4, **no REST-based evidence was gathered for this phase at all** — not for the plain reads (`dashboard`/`players`/`organizers`/`referees`/`associates`/`events`, which lean on the pre-existing, already-proven `profiles_select_admin`/`profiles_select_org_via_*` RLS policies from M5 Step 1 and carry the same risk profile as every other role's list query already verified elsewhere), and not for the two Edge-Function-backed writes (`createUser`/`updateUser`/`deleteUser`), which is the deliberate, instructed gap. What stands behind this phase is: a clean `build`/`lint`, careful reading of the live RLS policies and both Edge Functions' actual source (not assumed), and the uuid-keying fix above, found and reasoned through the same way every prior real bug in this project was — by reading, not by running.
